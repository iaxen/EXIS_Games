# Zombie Rush Survival: map boundary, layered defenses and teleport dodging

## Area controls

AREA contains **Pick Map Part**, **Edit Saved Boundary**, and a persistent **Show Saved Boundary** switch. Off removes the world markers; on draws the current map's saved boundary. Visibility is independent of Master and does not change the selected polygon or interrupt a placement by changing the layout revision. Closing or cancelling the editor respects the switch instead of automatically showing markers. Map changes refresh the displayed boundary.

The independent map replica retains mouse/touch selection, immediately visible numbered corners, CONNECT, undo, clear, cancel, zoom/pan, and real floor controls. Pick Map Part generates the clicked source part's four corners. Edit Saved Boundary reloads the saved corners. Opening the editor keeps combat active. The removed Area actions were new free-form selection, separate show/hide buttons, and removing the map-part lock. Old saved regions remain readable; the saved part remains the placement surface. The legacy automatic spawn-area override is disabled so it cannot silently replace the selected area.

## Final defense layout

The requested layout is **one outer barricade row plus three turret rows behind it**, with spaced middle defenses rather than solid interior tiling. Middle barricade anchors are approximately **12 studs apart by default**, with nearby shooting defenses, including missile defenses when exposed by the equipped class and enabled. Selected traps can use remaining space beside these groups. Native grid snapping may offset the anchor by part of a stud. Middle Defense Spacing is adjustable from 6–40 studs.

Ordinary Barricade, FlameBarricade, ExplosiveBarricade and other barrier names are classified as walls even when Classification.Barricade is absent. The supplied ordinary Barricade has Style=Barrier, Physics.ZombieBlocking=true, and FakeWall.Enabled=true; the previous classifier incorrectly treated it as a turret. Nonblocking support barricades are not credited as a blocking outer wall.

For an axis-aligned rectangular map part, the planner creates aligned frame rows using the native footprints. Adjacent defense grid cells can touch each other. The drawn selection is an outer limit: runtime planning adds a one-stud inward gap and grid-aligns rectangular bounds inward; defenses cannot touch or cross the drawn lines. This avoids the artificial 0.3-stud spacing and greedy corner holes in the earlier planner. Turret frames shrink behind the actual barricade dimensions, preserving three separate rows. Other valid polygons use inward offset rows and interval-based gap checks. Collapsed, narrow, concave or otherwise unsupported offsets are reported rather than bridged with imaginary placements.

Per-slot facing follows the native contract: only types supported by DeployablePlacement.FacesCharacter can rotate in the general polygon planner. Native nonrotating barricades keep facing zero. Placement sends the chosen slot's facing, not one shared orientation derived from the first boundary edge. Every requested point is re-snapped to its native grid and its complete footprint is checked strictly inside the original polygon before the native Place call, alongside surface, occupancy, safety, cash reserve, class and map checks.

A selected support unit gets actual reserved space; classes without support do not leave a phantom support hole. The geometric blueprint is cached independently of live occupancy. Confirmed and pending defenses mask occupied slots; destroying a defense reopens the same original slot without shifting the rest of the layout. Late-loading templates, class/map changes, selected defense changes and middle-spacing changes invalidate the blueprint. Rejections use map/revision/type/coordinate/facing keys and preserve their backoff.

There is no script-owned defense count ceiling, including legacy saved limits. The planner fills its existing outer barricade, three inner turret rows and spaced middle groups according to the selected geometry. It builds affordable defenses before ordinary upgrades, with urgent health and boss combat retaining priority. An unaffordable first turret can give way to another affordable planned defense. When all planned slots are occupied it waits and resumes after space reopens; native prices, placement rules and cash reserve still apply.

Placement uses the native DeployablePlacement.GetPlacementDistances range rather than forcing the character onto an arbitrary side point first. A selected, supported floor is valid for its building approach even outside the conservative spawn-point hull; physical floor, collision, footprint and enemy checks remain active. Placement safety uses predicted attack reach plus a margin rather than the wider combat comfort radius. Height checks prevent ordinary enemies far below a roof from blocking it, while retaining large boss reach. Safe build approaches outrank random teleport openings. The character briefly holds position during the Place response; urgent danger can interrupt. Successful placements can proceed again on the next worker tick without the generic one-second purchase delay.

## Fight mode teleport dodging

Fight defaults to **Teleport Dodge in Fight Mode**, with preferred zombie clearance **35 studs** and a normal TP interval of **0.3 seconds**. Clearance is adjustable from 3–40 studs; interval from 0.12–1 second. Disabling this option retains the previous grounded turret-aware dodge mode. No hover or high-altitude flight is created.

Fight checks threats on a 0.1-second cadence and relocates repeatedly while enemies exist, even when its old spot remains clear. Candidate positions include nearby rings, native navigation points and a coarse spread across the playable map. A recent-location penalty discourages repeatedly attracting the swarm to one spot. Friendly turret coverage is a small preference; empty space and attack clearance take priority. A safe placement approach can be chosen as a landing so defense work can still progress.

Destination scoring uses all available visual zombie positions, native attackRange, and recent movement projected over the TP interval. Zombie motion is estimated from replicated visual displacement, with extreme visual jumps bounded against the native speed reference. It prefers the requested empty radius; if unavailable, a smaller opening is eligible only when predicted attack clearance remains positive with body/safety margin. Boss reach is included. Newly arrived enemies and the character are checked again immediately before teleporting.

Landing validation requires a playable-map floor, a clear character-sized volume using the player's collision group, and nine solid-floor support samples around the body, including diagonal corners and a one-stud edge margin. Walls, collidable deployables, holes, water, steep support and excessive drops reject the landing. Rejected cells have a short backoff. A landing ray searches only 12 studs down and the destination floor may differ from the current floor by at most three studs. Decorative or non-colliding surfaces are excluded using the character collision group. Walking checks full endpoint footprints plus a dense center/shoulder strip at two-stud intervals, with bounded query counts. Invalid routes cancel horizontal momentum while preserving vertical velocity. The scan and expensive landing queries are bounded. Normal TP cooldown remains enforced, with a 0.12-second minimum emergency relocation when a new threat or damage arrives. Anchored, seated, PlatformStand, Physics, Ragdoll, Dead, stopped and disabled states cannot issue teleport movement.

Teleport cancels the outstanding walk, preserves orientation, lands at normal standing height and clears residual velocity. It does not alter zombie AI or health. Gun selection, firing, reload and boss targeting continue independently; the old hold-near-turret walk does not resume after a TP. With no enemies it does not roam unnecessarily, while a safe build approach can still move. When no validated opening is found it reports that and continues rechecking/firing.

Actual server acceptance, latency, special boss abilities beyond the exported attack range, and live executor behavior remain unverified. These are local movement requests and cannot guarantee zero damage or survival.

## Source and verification

The implementation uses the supplied CrystalMap and SkylineCity exports, including DeployableDefinitions, DeployablePlacement, DeployableUtils, ClassDefinitions, ZombieTypes and native map/navigation geometry. Their matching shared contracts were checked previously. The universal Fuzzotopia-style EXIS shell and existing per-game save paths remain in use. README is unchanged.

The current ZombieRushSurvival verification has 174 mocked checks across eight suites, including strict interior placement for rectangular, fractional, rotated and concave selections. It covers existing map/editor, combat and native adapters, plus unlimited plans over 512 slots, exact destroyed-slot replacement, a full-area wait/resume cycle, late templates, affordable candidates beyond the first 32 expensive slots, native range, cash rechecks, active selected-floor approaches outside the spawn hull, building versus dodge priority, and holding safely during a placement request. The complete module also passes the local Lua compilation check. Live Roblox placement and executor behavior still need testing.

Diagnostics is now the final sidebar category in both MrBeast and ZombieRush. See [Game Diagnostics](Game_Diagnostics.md) for full-session export and persistence behavior.
